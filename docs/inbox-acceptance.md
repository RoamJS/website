# RJS-03 private suggestion inbox

The owner workspace is `/admin/suggestions`. It supports search, status filters, 25-item pages, full suggestion/contact details, statuses (new, reviewing, planned, completed), private follow-up notes, and manual email replies. Opening an email draft does not record a sent message. The owner explicitly checks “I sent a reply” and saves to record the server timestamp. This is a manual follow-up log, not proof of email delivery.

## Access and data

Migration `20261007020345_suggestion_owner_inbox.sql` extends the existing private suggestions table and creates `private.website_owners`. It is applied to the existing project `uxihswugvmdwbbtgxtfl` in organization `jevettuehuhgoesqqhxc`. The user-designated owner email was configured privately, outside source control. No email was sent and no real user account was created.

An administrator manages the exact lowercase verified-email allowlist using the authorized database connection. It is intentionally empty on fresh migration; populate it separately after confirming the intended owner. Membership follows the current verified email in `auth.users`: changing away from that email removes access. No user metadata claim grants ownership. Never expose owner-list writes to website clients. Remove the allowlist row to revoke access.

The server page verifies the session using Supabase Auth before rendering any inbox markup. Signed-out or unverified visitors are redirected to `/account?next=inbox`; verified nonowners receive the not-found page. The database owner authorization also runs before rendering. Both code and same-browser email-link sign-in return to the inbox when requested. The latter uses a one-hour, fixed-destination callback cookie, cleared after use; it contains no identity data and never grants access. The APIs verify the session independently. Database functions independently derive the current verified, non-anonymous email and check the private owner table on every read/write. Public wrappers are security invoker; narrowly scoped private functions use security definer with an empty search path to access tables that clients cannot access directly. Both tables have RLS and no anonymous/authenticated table grants. Authenticated function execution alone does not grant access to data. No service-role key is used by the website.

All API responses are private/no-store. The route is excluded by the analytics public-path allowlist, private UI elements are marked to prevent capture, and search terms/contact details are not stored in browser storage. Private pages are noindex and carry session-refresh/no-store handling. Updates use a version check to reject stale writes; failed saves preserve the draft. A conflict offers an owner-authorized latest-review lookup and an explicit choice to keep the local draft or use the saved version before retrying. Unsaved editor drafts survive client navigation and browser history in account-scoped memory, are cleared on sign-out/account change, and never enter browser storage. Normal link navigation warns before leaving; full-page exits use the browser unload warning. Drafts do not survive a full page reload or closing the browser.

## Verification

- 90 unit/API/server-page tests cover verified identity, owner denial, private caching, bounded filters/pagination, CSRF, invalid/spoofed writes, stale/missing rows, unavailable storage, missing receipts, and safe mailto headers.
- Hosted `supabase/tests/inbox-security.sql` passed before and after applying the migration. Actual Postgres `authenticated`/`anon` roles prove owner list/update, explicit contact timestamp, conflicts, validation, denied direct table access, denied self-promotion, and denied ordinary/unverified/anonymous accounts. Synthetic Auth users, owner grants, and suggestions are transactionally rolled back.
- Four independent browser component fixtures pass navigation/history restoration, sign-out clearing, conflict reconciliation with a new version, explicit discard, and expired-session recovery revalidating auth, showing the sign-in form and returning to the inbox after code verification. They render the real editor/draft provider and AuthProvider/AccountForm with synthetic Supabase/API fixtures in a test-only Vite server; no production auth bypass is present. Run `npm run test:inbox-recovery`.
- Five auth browser cases pass, including a fixed return hint, callback failure recovery, and delivery-failure cleanup. Email requests are intercepted; no real emails are sent.
- The signed-out browser redirect check passes with no inbox markup or inbox API request. Production build, lint and typecheck passed. Earlier owner workflow checks passed before the new server gate. Rerunning the three authenticated browser cases now requires a real owner session file via `INBOX_BROWSER_STORAGE_STATE`; API interception cannot bypass server-rendered access checks. Browser tests use API fixtures for the owner workflow, failed-save retry, follow-up checkbox, search/filter/pagination, denied/signed-out states, and mobile width. They do not establish real owner email delivery.
- Existing `public.apps` and `public.oauth_clients` RLS/GraphQL advisories are unchanged and remain outside this task. RLS-without-policies information notices on private tables reflect deliberate default-deny table access.

## User acceptance

Sign in with the designated verified owner email on the protected preview, then open `/admin/suggestions`. Review a real idea, change its status, open a reply in your mail app, and record follow-up only after sending. Real inbox sign-in still depends on the RJS-01 email acceptance/custom SMTP work. Production sign-in and public community activation are not part of this PR. Newsletter signup remains unavailable.
