# RJS-10: protect account email requests

The account form can send Supabase Auth a Cloudflare Turnstile token with each email request. Supabase must enforce that token before this becomes an abuse control: the browser calls the public Auth endpoint directly, so a website-only challenge can be bypassed. This change does not affect newsletter signup or suggestion submission.

The RJS-10 investigation found 39 non-test accounts created during a seven-day period without recorded completed sign-ins, and three spam complaints among 53 account-wide sent emails. These counts support protecting the initial Auth request, but do not identify all 39 accounts as bots. The investigation's local HTML briefing is intentionally excluded from the repository.

## Configuration and order

1. Confirm the RoamJS/Cybrarian organization `jevettuehuhgoesqqhxc` and the existing RoamJS Supabase project `uxihswugvmdwbbtgxtfl`. Do not create another project.
2. In Cloudflare Turnstile, create one **Managed** widget with only the production host and the stable protected preview host(s) that will be tested. Cloudflare DNS or hosting is not required. Store the widget's **public site key** as `NEXT_PUBLIC_AUTH_TURNSTILE_SITE_KEY` in the corresponding Vercel environments and rebuild each deployment. This key is public. Keep the **secret key** out of source, `NEXT_PUBLIC_*`, chat, and Vercel browser settings; enter it only into the Supabase Auth CAPTCHA provider configuration when enabling enforcement.
3. Deploy the token-capable form to every current website environment that uses this shared Supabase Auth project. If any other client uses the same project, update it too before enforcement. A protected Vercel preview is **not** a separate Supabase CAPTCHA sandbox. With the hosted toggle still off, test that the widget loads, errors recover, and email requests carry a fresh token. Use Cloudflare's [testing site key](https://developers.cloudflare.com/turnstile/troubleshooting/testing/) for local browser tests; keep test keys out of production.
4. Check the exact production and preview hostnames, then turn on **Authentication → Attack Protection → Enable Captcha protection** in the existing Supabase project, select Turnstile, enter its secret key, and save. This is a project-wide change. Immediately verify that valid signup and returning sign-in requests work. A direct Auth email request with a missing, invalid, expired, or reused token must fail without sending mail. Use only controlled test addresses.
5. Check code verification, same-browser email links, session reload, owner inbox return, sign-out, narrow-screen layout, keyboard navigation, and a blocked or timed-out widget. Check that no token appears in analytics, logs, or repository evidence. Compare Auth sends, complaints and bounces with completed sign-ins and suggestions daily during the first week, then return to the existing weekly spam check.

The account form resets its Turnstile widget after every email request, including provider failures. Missing or expired tokens never call `signInWithOtp` when the public site key is configured. Supabase's server-side enforcement is the real boundary; browser checks alone do not stop direct callers. Keep the existing Supabase Auth rate limits and Resend complaint/bounce suppressions in place.

If valid users cannot sign in after activation, **turn off the Supabase CAPTCHA requirement before reverting the token-capable website form**. Restore the recorded hosted settings. If Turnstile fails to load while enforcement is on, the form gives a retry/reload path and does not send an unverified email request.

Sources: [Supabase CAPTCHA](https://supabase.com/docs/guides/auth/auth-captcha), [Turnstile explicit rendering](https://developers.cloudflare.com/turnstile/get-started/client-side-rendering/), [Turnstile server verification](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).
